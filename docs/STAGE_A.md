## 2. Регистрация приложения

`https://oauth.yandex.ru/client/new` → платформа **«Веб-сервисы»**.

Запрашиваемые доступы — **только два, оба на чтение**:

| Доступ | Зачем |
|---|---|
| `cloud_api:disk.read` | чтение содержимого Диска (обход, метаданные, временные ссылки) |
| `cloud_api:disk.info` | сведения о диске: объём, занято, свободно |

`cloud_api:disk.write` и `cloud_api:disk.app_folder` **не запрашиваются**:
запись на Диск программе не нужна, а лишний доступ — лишний риск.

Более узкого доступа «только метаданные» API не предусматривает — `disk.read`
это минимум для чтения структуры.

## 3. Выбранный OAuth-сценарий

**Authorization Code Flow + PKCE (`code_challenge_method=S256`).**

```
GET https://oauth.yandex.ru/authorize
    ?response_type=code
    &client_id=<ClientID>
    &redirect_uri=https://oauth.yandex.ru/verification_code
    &scope=cloud_api%3Adisk.read+cloud_api%3Adisk.info
    &device_id=<устойчивый UUID>
    &device_name=Yandex%20Disk%20Backup
    &state=<случайная строка>
    &code_challenge=<S256(code_verifier)>
    &code_challenge_method=S256
```

Почему так:

1. **Документация прямо называет этот сценарий подходящим для консольных
   приложений** («запрос OAuth-токена при помощи кода подтверждения …
   консольные приложения»), в отличие от «мгновенной авторизации» (веб) и
   LoginSDK (мобильные).
2. **PKCE снимает необходимость в client_secret.** В документации по обмену
   кода на токен сказано прямо: *«Если … применяется расширение PKCE и в
   запросе передаётся параметр `code_verifier`, то секретный ключ передавать
   не требуется»*. Значит, в коде и конфиге нет секрета приложения —
   требование ТЗ выполнено конструктивно, а не запретом.
3. **Код живёт 10 минут** — окно для перехвата кода минимально.
4. **Отладочный токен** (`response_type=token`) документация называет
   средством для этапа разработки, и он не обновляется. Для программы,
   которая должна работать месяцами, это не подходит; он не используется.

### Redirect URI

`redirect_uri` должен **точно** совпадать с одним из URI, указанных в
настройках приложения; при несовпадении параметр игнорируется и берётся
первый URI по умолчанию. Поэтому в конфиге по умолчанию стоит URI, который
Яндекс предлагает сам: `https://oauth.yandex.ru/verification_code`
(значение «Подставить URL для отладки»).

Следствие: код подтверждения показывается на странице Яндекса, и его вводит
в консоль пользователь. Это штатный сценарий «код от пользователя» из
документации, а не обход авторизации.

Альтернатива (`auth_mode=loopback`, локальный сервер на 127.0.0.1)
поддержана в коде, но требует, чтобы этот точный URI был внесён
в настройки приложения, и включается явно.

### device_id / device_name

Документация предупреждает: у приложения не может быть больше 30 токенов,
привязанных к устройствам одного пользователя; при выдаче нового самый
старый перестаёт работать. Программа поэтому генерирует `device_id` один раз
и сохраняет его в `config.json` — повторные авторизации не плодят новые
устройства.

## 4. Обмен кода на токен

```
POST https://oauth.yandex.ru/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=<код>
&client_id=<ClientID>
&device_id=...&device_name=...
&code_verifier=<исходная строка>
```

Ответ: `access_token`, `token_type` (всегда `bearer`), `expires_in`,
и, если приложению его выдают, `refresh_token`.

## 5. Обновление и отзыв токена

```
POST https://oauth.yandex.ru/token
grant_type=refresh_token&refresh_token=...&client_id=...&[client_secret=...]
```
Коды ошибок: `invalid_client`, `invalid_grant` (токен просрочен/чужой/невалиден),
`invalid_request`, `unauthorized_client`, `unsupported_grant_type`.

```
POST https://oauth.yandex.ru/revoke_token
access_token=...&client_id=...&[client_secret=...]
```

По ТЗ: если refresh невозможен — требуется повторная авторизация. Именно так
и сделано: при `invalid_grant` или отсутствии refresh-токена программа
не пытается перебирать варианты, а прямо просит авторизоваться заново.

## 6. REST API Диска

Базовый URL: `https://cloud-api.yandex.net/v1`
Обязательные заголовки: `Accept: application/json`,
`Content-Type: application/json`, `Authorization: OAuth <token>`.
Другие MIME-типы API не поддерживает.

| Метод | Назначение | Стадия |
|---|---|---|
| `GET /v1/disk` | объём, занято, свободно, корзина, лимиты | **B** |
| `GET /v1/disk/resources` | метаданные ресурса и листинг папки, `limit`/`offset`/`sort` | D, E |
| `GET /v1/disk/resources/download` | временная ссылка на скачивание | II |

Пути: `disk:/...` — видимый Диск, `app:/...` — папка приложения.
Листинг возвращает `_embedded.items`, а также `_embedded.total`, `limit`,
`offset` — то есть пагинация через `offset`, и `total` известен заранее.

### Поля объекта Resource

`name`, `path`, `type` (`file`/`dir`), `size`, `mime_type`, `media_type`,
`created`, `modified`, `md5`, `sha256`, `revision`, `resource_id`, `file`,
`public_key`, `public_url`, `owner`, `preview`, `exif`, `custom_properties`.

**Важная находка для части II:** в объекте Resource заявлены `md5` и `sha256`.
Если API действительно отдаёт их для пользовательских файлов — это готовый
механизм проверки целостности при скачивании, а не вычисление хешей локально.
Но документация не гарантирует их наличие в ответе, поэтому код обязан
считать хеш необязательным полем и явно отмечать файлы без контрольной суммы
(это уже требование п. 16 ТЗ). **Проверяется на этапе D.**

Код не полагается на наличие ни одного поля: отсутствующее значение
помечается как неизвестное, а не заменяется выдуманным нулём.

## 7. Обработка ограничений

Числовые лимиты в доступных страницах документации не опубликованы, поэтому
клиент не зашивает «магические» числа, а ведёт себя так:

* троттлинг: минимальный интервал между запросами (по умолчанию 0.25 с);
* повторные попытки для 408, 425, 429, 500, 502, 503, 504 и сетевых сбоев,
  с экспоненциальной задержкой, джиттером и потолком;
* учитывается `Retry-After` (число секунд или HTTP-дата);
* если сервер присылает `X-Rate-Limit-Degree-Remaining` и
  `X-Rate-Limit-Degree-Reset` — ожидание вычисляется по ним;
* 401/403/404/423 считаются фатальными: повтор их не исправит, они
  превращаются в конкретное сообщение для пользователя.

## 8. Открытые вопросы (проверяются на реальном аккаунте)

1. Точный состав полей ответа `GET /v1/disk` — печатаются те, что вернулись.
2. Максимальное допустимое значение `limit` для `/v1/disk/resources`
   (в коде пока безопасное умолчание, см. этап D).
3. Приходят ли реально `md5`/`sha256` в листинге пользовательских файлов.
4. Выдаётся ли `refresh_token` при обмене кода из этого сценария.
5. Поведение при превышении лимита: какие заголовки реально приходят.
6. Видна ли корзина и опубликованные ресурсы — нужно ли `include_trash`.

Пункты 1–4 проверяются прямо на следующих этапах и в журнал попадают только
имена полей, без токена.
