# Часть II: как реализованы скачивание, возобновление и проверка целостности

Документ отвечает на вопрос «почему именно так», а README — на вопрос «как
запустить». Здесь описаны решения, которые на первый взгляд выглядят
избыточными, но каждое закрывает конкретный способ потерять данные.

## 1. Файл всегда сначала во временный, потом на место

```
.Reserve ─►  файл.photo.part.part ─► проверка размера и хеша ─► os.replace ─► файл.photo
```

Причина: единственный способ гарантировать, что незавершённый файл никогда
не окажется под финальным именем, — не давать финальному имени появиться
раньше проверки. Отдельный файл рядом с целью (а не во временном каталоге
системы) нужен ещё и потому, что `os.replace` требует один том — иначе
пришлось бы копировать, и появилось бы окно, в котором файл на месте, но
непроверенный.

Файл проверяется **до** перемещения. Если хеш не совпал, временный файл
удаляется, финальное имя не появляется, в реестр пишется `error`.

## 2. Сверка: сначала размер, потом хеш

* Размер сверяется всегда, если API его вернул. Это дешёвая проверка, которая
  ловит обрыв связи и недокачанный файл.
* Хеш сверяется, только если API его вернул (`md5`, иначе `sha256`).
* Если хеша у файла нет, файл всё равно сохраняется — но попадает в раздел
  «Файлы без контрольной суммы» отчёта. Молча считать такой файл идеально
  проверенным нельзя: это была бы ложь в отчёте.

Открытый вопрос из этапа A (`docs/STAGE_A.md`, п. 3) в реальности выяснится
на вашем аккаунте: приходят ли `md5` для обычных фотографий. Программа в
обоих случаях работает одинаково.

## 3. Коллизии имён: три стратегии, ни одна не удаляет данные

| Стратегия | Что делает |
|---|---|
| `keep` (по умолчанию) | Существующий локальный файл не трогаем. Облачный файл сохраняется рядом с суффиксом ` (2)`, причина попадает в отчёт. |
| `replace` | Заменяет файл, только если тот не подтверждён как верный. Проверенный файл защищён. |
| `overwrite` | Перезаписывает безусловно. Включать осознанно. |

Переименование — не деталь реализации: причина всегда попадает в результат
и в отчёт, чтобы пользователь не гадал, почему файл лежит под другим именем.

Дополнительно безопасное имя приводится к виду, допустимому на Windows:
недопустимые символы заменяются, хвостовые точки и пробелы убираются,
зарезервированные имена (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`,
`LPT1`–`LPT9`) обезличиваются, длина ограничивается. Сравнение имён
регистронезависимое и с нормализацией Unicode — иначе `IMG.JPG` и `img.jpg`
слились бы в один файл на NTFS.

Имена стабильны между запусками: при старте распределитель загружает
назначения из реестра состояний, поэтому докачка после обрыва попадает в
тот же файл.

## 4. Возобновление: состояние в SQLite

Таблица `files` в `state.db` хранит по одной записи на файл:

```
pending → downloading → downloaded → verified
                  ↘ error / recheck / changed
```

Ключевые свойства:

* при старте все `downloading` возвращаются в `pending` — после аварийного
  завершения прерванный файл не может числиться сохранённым;
* перед началом крупной работы сверяется реальное состояние локального диска:
  `verified`-файл, которого нет на месте или размер которого не совпал,
  возвращается в работу;
* `verified` снимается только при изменении размера, даты или хеша в облаке —
  и только для файлов, которые реально были доведены до конца;
* перед загрузкой проверяется свободное место: не хватает с запасом —
  загрузка не начинается вовсе, а не падает на середине.

## 5. Докачка через HTTP Range — выключена по умолчанию

ТЗ требует: докачка допустима «только при подтверждённой поддержке сервером
HTTP Range и корректной проверке ответов». Поэтому по умолчанию файл
скачивается заново, а `allow_range_resume` (пункт `D` в меню) включает
докачку только при выполнении всех условий:

1. запрос сделан с `Range: bytes=N-`;
2. сервер ответил `206`, а не `200`;
3. заголовок `Content-Range` начинается ровно с `bytes N-`;
4. при любом несовпадении частичный файл отбрасывается и файл качается
   целиком.

Иначе для 180 ГБ экономия обычно не окупает риск: средний размер фотографии
невелик, а повреждённый «докачанный» файл обнаружится позже и дороже.

## 6. Истёкшая временная ссылка — не ошибка

Ссылка `GET /v1/disk/resources/download` живёт ограниченное время. Отказ
CDN (401/403/404/410) трактуется как «ссылка устарела»: берётся новая ссылка,
файл скачивается заново. Сеть и ошибки 5xx — с экспоненциальной задержкой и
джиттером, до `max_attempts_per_file` попыток.

Ограничения API учитываются по заголовкам: `Retry-After`, а если пришли
`X-Rate-Limit-Degree-Remaining` / `X-Rate-Limit-Degree-Reset` — пауза
считается по ним. Плюс общий троттлинг по `min_request_interval`.

## 7. Параллельность

`concurrency` потоков (по умолчанию 4). У каждого потока свой
`requests.Session` — сессия не потокобезопасна, и общая привела бы к тихим
сбоям. Троттлинг общий для процесса.

Одна загрузка на файл; на диск пишется `O_SYNC` перед перемещением, поэтому
внезапное отключение питания не оставит «проверенный» файл с незаписанными
данными.

## 8. Остановка и продолжение

`Ctrl+C` во время обхода или загрузки ставит мягкий флаг: текущий файл
дорабатывается или отбрасывается, состояние пишется, программа завершается
нормально. Повторный `Ctrl+C` — выход немедленно. Дальше `python main.py`
(пункт `6` или `A`) продолжит с того места.

## 9. Что программа не делает принципиально

* не удаляет, не перемещает и не изменяет файлы в облаке — в коде нет ни
  одного запроса к Диску кроме `GET`;
* не создаёт единый ZIP-архив: каждый файл скачивается отдельно;
* не перекодирует содержимое: байты сохраняются как есть;
* не удаляет существующие локальные файлы автоматически;
* не отправляет содержимое никуда: анализа, распознавания и внешней
  отправки в коде нет;
* не хранит пароль пользователя — только OAuth-токен, в отдельном файле
  с ограниченным доступом, и никогда не печатает его.

## 10. Где смотреть результат

* `%LOCALAPPDATA%\YandexDiskBackup\report.md` — человекочитаемый отчёт;
* `%LOCALAPPDATA%\YandexDiskBackup\report.json` — то же для машин;
* `%LOCALAPPDATA%\YandexDiskBackup\manifest.json` — что есть в облаке;
* `%LOCALAPPDATA%\YandexDiskBackup\manifest.prev.json` — предыдущий обход
  для сверки (появляется после пункта `9`);
* `%LOCALAPPDATA%\YandexDiskBackup\state.db` — состояние каждого файла;
* `%LOCALAPPDATA%\YandexDiskBackup\backup.log` — журнал, секреты замаскированы.
